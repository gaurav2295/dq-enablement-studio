## What it is

The record shape used by `syniti-dq-rule-repo`, the single Syniti DQ best-rules catalogue.
Every entry mirrors dq-studio's `CatalogEntry` — the same name, business-text and
classification fields — plus this repository's own additions for provenance and linkage.
Consumers ([[gls-dq-studio|dq-studio]], bob-canvas, the rule explorer) never read the catalogue
file directly; they go through an API layer instead.

## Field groups

**Identity & business text**

| Field | Holds |
|---|---|
| `adm_rule_name` | The business name — see [[gls-adm-rule-name]]. **Not** a technical view or table name. |
| `rule` | The business statement of what the rule checks. |
| `implication` | The ~40-word / 2-3 sentence business impact — see [[gls-implication]]. |
| `description` | The full Fetch/Check/Return description, where one exists — deliberately separate from the short `implication`. |

**Classification**

| Field | Holds |
|---|---|
| `rule_type` | `Error` \| `Info` — the enum has no Profiling value. |
| `subject_area` | Business-area classification. |
| `business_process` | Process classification. |
| `sub_business_process` | Finer process classification. |
| `primary_data_object` | The master/transactional object the rule primarily concerns. |

**Evidence hints**

| Field | Holds |
|---|---|
| `tables[]` | SAP table identifiers, only where known from the source — never invented; filtered against SQL-keyword/schema-name noise. Empty is correct and common. |
| `industry[]` | Researched industry applicability — never invented; empty if nothing defensible. |
| `compliance_refs[]` | Researched compliance references — same honesty rule. |

**Provenance** — see [[con-rule-provenance-model]] for the full model.

| Field | Holds |
|---|---|
| `provenance` | Whether the rule's *existence* is field-evidenced or catalogue-derived. |
| `name_source` | Whether `adm_rule_name`'s *text* was freshly generated or copied from the catalogue. |
| `implication_source` | Same distinction, applied to `implication`. |
| `agent_decided` | Optional flag set when an agent made a judgment call rather than a source having settled it. |

**Linkage** — one structured field joining the rule into the value chain (see
[[con-value-chain]] and [[ref-key-issue-vocabulary]]):

```
linkage:
  outcome_category
  value_lever
  key_issue_ids: [...]
  edges:
    - target: <lever: or key_issue: or outcome: id>
      confidence: 0-1
      method: <how the edge was decided>
```

The README documents `method` as `lexical` | `adjudicated`. That enum is the narrower, earlier
reading: per ADR 0002's L5 provenance principle, an applied edge's `method` also carries the
deciding principle id and date, not just a bare label — so a governed edge is auditable back to
the ratification that produced it (see [[prn-governed-ratification]]). Empty linkage is an
honest, legitimate outcome: coverage gaps are reported, never papered over by forcing an edge.

**Matched-record bookkeeping** — two further identifiers `_meta` calls out for records
reconciled against a pre-existing field-proven source:

| Identifier | Holds |
|---|---|
| `canonical_key` | The field-proven source's stable key. Matched records are keyed by it in the catalogue rather than by `adm_rule_name`, because the matched technical name is not unique across matched records. Wave-origin records are keyed by `adm_rule_name`. |
| `name_pending` | `true` when `adm_rule_name` for that record is still the technical `matched_adm_rule_name` as a placeholder, never generated by the naming pipeline. Never treat a `name_pending` record's `adm_rule_name` as business-compliant. |

> [!note]
> The groups above are the fields the README and `_meta` describe, not a closed schema listing —
> neither source publishes an itemised field list, and records carry additional bookkeeping keys
> beyond those documented. Read this as the documented core, not as an exhaustive field count.

## What is deliberately NOT in the repository

- **Rule SQL.** No check logic — no `op_query_sql`, no `report_query_sql` — appears anywhere in
  this schema. This is a scope boundary, not an oversight: the repository is a rules *library
  and value graph*, not a rule *execution engine*. dq-studio's own catalog carries both T-SQL and
  HANA query pairs per entry; this repository deliberately does not. A future *technical* view
  name would get its own field, `adm_view_name`, only when SQL generation starts downstream of
  this data — it is not part of the current schema.
- **Client data.** No client names, project codes, account numbers, or financial figures appear
  anywhere. The pipeline that assembles the catalogue runs a deny-list sanitisation pass with a
  zero-hit gate before any commit.
