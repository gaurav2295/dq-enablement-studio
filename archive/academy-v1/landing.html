What is Data Quality?

Data Quality (DQ) is the degree to which data conforms to defined standards and meets business expectations. It's not a single metric—it's a multidimensional measurement.

Key Definition

"Data Quality is the fitness of data for a business purpose. Poor quality data costs your organization in rework, regulatory fines, customer churn, failed migrations, and bad decisions."

Why DQ Matters (In One Sentence)

A single bad record in your master data can break downstream processes, analytics, compliance checks, and entire migration projects.

Common Consequences of Poor DQ

  • Rework: Manual data cleanup takes weeks or months
  • Regulatory Risk: Non-compliance with GDPR, HIPAA, SOX
  • Operational Failures: Orders not fulfilled, shipments delayed, invoices uncollectable
  • Migration Delays: ERP migrations fail or stall when data isn't clean
  • Bad Decisions: Analytics and reporting built on dirty data leads to wrong strategies

In the Context of SAP Migrations

When organizations migrate from SAP ECC to S/4HANA, master data quality is the single biggest risk factor. Projects fail or stall because:

  • Master data hasn't been validated before migration
  • Orphaned records exist (foreign keys without parents)
  • Required fields are missing or invalid
  • Duplicate records confuse business logic

Data Quality Rules are how you prevent this. They codify what "bad" means and let you catch issues early, before they cascade downstream.

The Six Dimensions of Data Quality

Data quality is multidimensional. These six dimensions cover the full spectrum of what "good data" means:

📊 Accuracy

Data reflects reality; values are correct for their context. A material's weight should match what's actually produced.

✓ Completeness

Required fields are populated; no critical nulls or gaps. Every vendor must have a tax ID; every material must have a UoM.

🔗 Consistency

Same data is uniform across systems and time. A customer's name is spelled the same in ECC, CRM, and Analytics.

🎯 Validity

Data conforms to defined formats, types, and ranges. Dates are valid, status codes are on the allowed list, numbers are positive.

⏰ Timeliness

Data is current and available when needed. Pricing updates are daily; inventory is real-time.

🔑 Uniqueness

No unwanted duplicates; keys are truly unique. Each material has one MATNR; each customer has one KUNNR.

In Practice

Your DQ rules will typically focus on one or two of these dimensions. For example:

  • A rule checking that a material's UoM exists in the valid list = Validity
  • A rule flagging vendors without a tax ID = Completeness
  • A rule detecting duplicate customer records = Uniqueness

The DQ Lifecycle

4
Recheck

Cycle Detail

1. Profile

You run a schema profile on your master data to understand:

  • How many records exist
  • What fields are null, empty, or unusual
  • What values appear most often (low vs high cardinality)
  • What distributions look abnormal

2. Rule

Based on profiling findings and business requirements, you define rules that codify what "bad" means. Each rule has:

  • A name (concise, business-friendly)
  • A description (what is being checked and why)
  • A logic (the error condition in SQL)
  • A scope (inclusions and exclusions)

3. Remediate

Once rules flag bad records, someone fixes them. This might be:

  • Automated: Recalculate a field, fill a null with a default, merge duplicates
  • Manual: Domain expert reviews and corrects the record
  • Process: Fix the upstream system that's creating bad data

4. Recheck

You run the rule again to verify the fix worked. This confirms:

  • The flagged records now pass
  • No new errors were introduced
  • The data is now fit for business purpose

Key insight: This cycle repeats. DQ is continuous improvement, not a one-off project.

What is a Data Quality Rule?

A DQ rule is a codified business check that flags records as "bad" if they violate a condition.

Rule Anatomy

Every DQ rule has these four components:

📛 Name

A concise, business-friendly name (max 100 chars, target 85). Example: "Material must have valid base unit of measure"

📝 Description

Follows the Fetch / Check / Return template. Explains what data is fetched, what condition is checked, and what the rule returns.

⚙️ Logic

The actual error condition, written in SQL. This is where you define what "bad" means in technical terms.

🔍 Scope

Inclusions (which records to check) and Exclusions (which records to skip). Deletions flags go here.

How Rules are Generated

Rules are expressed as SQL views:

  • OptSel: The "options" view. Returns ALL candidate rows with a zIsErrorFlag (1=error, 0=clean).
  • RptSel: The "report" view. A simple wrapper: SELECT * FROM OptSel WHERE zIsErrorFlag = 1. Only errors.

Who Writes Rules?

In the Syniti workflow:

  • Business Analysts / Data Stewards define the rule in business terms (what data should look like)
  • The Studio (powered by AI or local derivation) generates the SQL automatically
  • Reviewers validate that the generated SQL matches the business intent

Important: Rules are not subjective opinions. They're measurable, business-defined conditions that execute reliably in SQL.

Common DQ Issues in SAP Master Data

These are the most frequent data quality problems encountered in SAP ECC and S/4HANA environments:

❌ Issue 1: Missing Foreign Keys

What: Foreign key values don't exist in the master table.

Example: A purchase order references a vendor that doesn't exist in the vendor master.

Impact: Downstream processes fail; reports show orphaned transactions.

❌ Issue 2: Orphaned Records

What: Links to deleted or non-existent parents.

Example: A material references a cost center that was deleted.

Impact: Costing breaks; cost allocations become invalid.

❌ Issue 3: Null Required Fields

What: Required attributes are empty or blank.

Example: A customer master record has no billing address.

Impact: Invoices can't be sent; orders can't be fulfilled.

❌ Issue 4: Invalid Status Codes

What: Values outside the allowed list.

Example: A material has status code "ACTIVE2" when only "ACTIVE", "INACTIVE", "PHASED_OUT" are valid.

Impact: Business logic based on status fails; filtering breaks.

Migration Impact

S/4HANA migrations fail when these issues aren't caught and fixed first. A typical migration can be delayed 30–90 days because bad data wasn't cleaned before cutover. The cost: rework, reputational risk, missed business objectives.

Key Concepts: OptSel vs RptSel

This is the most important architectural concept in DQ rule design. Understand this, and everything else makes sense.

✓ OptSel (The Universe)

Purpose: Returns every row that matches your scope, whether clean or dirty.

Key Column: zIsErrorFlag (1 = error, 0 = clean)

Computed via: CASE WHEN <error_condition> THEN 1 ELSE 0 END

Use case: Audit both good and bad records from one view. Compare trends over time.

✗ RptSel (Errors Only)

Purpose: Simple wrapper that filters OptSel to only errors.

Query: SELECT * FROM OptSel WHERE zIsErrorFlag = 1

Result: Smaller, focused result set of just the problems.

Use case: What remediation and auditors work with. What gets reported to business.

Why This Split?

The separation of concerns is powerful:

  • Measure everything (OptSel) — you can see the full picture: how many clean, how many errors, what's the trend.
  • Report only problems (RptSel) — action is taken only on the errors; nobody needs to see the clean records.

Other Key Concepts

🚩 Error Flags

zIsErrorFlag is always INTEGER (1 or 0), never TEXT ("Yes"/"No"). This ensures:

  • Consistent handling in downstream logic
  • Easy aggregation and counting
  • Predictable behavior in filters

🗑️ Deletion Flags vs Status Fields

These are treated differently in rules:

  • Deletion Flags (LVORM, LOEKZ, LOEVM) → go in WHERE clause (exclude deleted records outright)
  • Status Fields (MMSTA, PSTAT, STATU) → drive the error flag in CASE (status determines if record is good or bad)

📋 Standard Field Sections

Every generated rule includes these sections in order:

  1. Syniti Technical Fields (zSourceSystemID, zConcatenatedKey, zIsErrorFlag — always these three, always first, always in this order)
  2. Basic Fields (core identification/descriptive attributes)
  3. Organizational Context (company code, plant, etc.)
  4. Value Context (amounts, codes, etc.)
  5. Activity Context (created by, dates, etc.)

Recognizing these sections helps you read any generated SQL at a glance. Session 2 (SQL Best Practices) covers this categorization in full detail.

A Rule in Action: Material Master Example

Let's walk through a real rule from start to finish.

The Rule

"Material must have a valid, non-deleted base unit of measure"

The SQL (OptSel)

WITH base_materials AS ( SELECT MANDT, MATNR, MEINS FROM mara WHERE LVORM = '' -- Exclude deleted materials ) SELECT MANDT, MATNR, MEINS, -- Syniti Technical Field CASE WHEN MEINS IS NULL THEN 1 WHEN MEINS NOT IN (SELECT MSEHI FROM t006 WHERE SPRAS = 'E') THEN 1 ELSE 0 END AS zIsErrorFlag FROM base_materials

What This Rule Does

  • Scope: All materials where LVORM (deletion flag) is empty (not deleted)
  • Check: MEINS (base UoM) must exist and must be in the valid UoM list (table T006)
  • Flag: zIsErrorFlag = 1 if MEINS is NULL or invalid; 0 if valid

Sample Results

This OptSel returns 100 materials, of which 15 have errors:

✓ Clean Records (zIsErrorFlag = 0)

M001 → MEINS = "KG" ✓ Valid unit

M002 → MEINS = "PC" ✓ Valid unit

M003 → MEINS = "L" ✓ Valid unit

...and 82 more clean records

✗ Error Records (zIsErrorFlag = 1)

M999 → MEINS = NULL ✗

M1001 → MEINS = "XYZ" ✗ Not in T006

M1002 → MEINS = "ZZ" ✗ Not in T006

...and 12 more error records

RptSel (The Report)

SELECT * FROM OptSel WHERE zIsErrorFlag = 1

RptSel returns only the 15 errors. These are what auditors and remediation teams use.

Next Steps (After the Rule)

  1. Review: Auditor looks at the 15 error records
  2. Remediate:
    • M999: Assign the appropriate UoM (e.g., "KG")
    • M1001, M1002: Fix the typo or assign valid UoM
  3. Recheck: Run the rule again → should show 0 errors now

Note: This simplified example is missing the mandatory zSourceSystemID filter and the full comment standard. Session 2 (SQL Best Practices) shows the complete, production-correct version of this exact rule.

Frequently Asked Questions

Here are common questions about DQ rules and the methodology:

Q: Who writes DQ rules?
▼
A: Business analysts and data stewards (with domain knowledge) define the rule in business terms. The Syniti Methodology Studio generates the SQL automatically. Reviewers then validate that the generated SQL matches the business intent.
Q: How often should I run DQ rules?
▼
A: It depends on your context:
  • In production: Daily, or before critical business processes
  • During migrations: Continuously while data is being cleansed
  • On-demand: After major data loads or system changes
Q: What's the difference between a rule and a validation?
▼
A:
  • Rule: A standing, reusable check that runs anytime (daily, ad-hoc, etc.). Can be applied to different datasets.
  • Validation: Often a one-time gate that checks a specific import or migration. Validation = "does this data load pass?" Rule = "does this data always meet these standards?"
In practice, rules are more powerful because they're reusable and measurable over time.
Q: What if a rule flags too many errors?
▼
A: You have a few options:
  • Reassess the rule: Maybe it's too strict or the business requirement was misunderstood. Refine the rule logic.
  • Accept the baseline: If the data baseline is worse than expected, accept it and plan remediation in phases.
  • Exclude a subset: If a certain domain or system has legitimately different data, add an exclusion to scope.
The key is to not just ignore high error rates—investigate the root cause.
Q: Can I automate remediation?
▼
A: Sometimes, but not always:
  • Automatable: Recalculate a field, fill a null with a default, merge exact duplicates, assign a default status.
  • Manual: Domain expert review (wrong data often has a reason), correcting typos, deciding which duplicate to keep.
Rule of thumb: Rules identify; humans (or smart logic) fix. Most remediation requires at least some domain judgment.
Q: How do I know if my DQ rules are "good"?
▼
A: Good rules have these properties:
  • Business-defined: Rooted in actual business requirements, not just technical constraints
  • Measurable: You can run the SQL and get a count of errors
  • Auditable: Someone can look at a flagged record and understand why it failed
  • Actionable: The error is something data stewards can actually fix
Bad rules are: Vague ("data should look nice"), technically infeasible, or so strict they're unusable. See Session 2's "What a Good Rule Looks Like" for a complete SQL-level checklist.
Q: What's the relationship between Profiling and Rules?
▼
A: They're sequential:
  • Profile first: Run a schema profile to see what your data looks like (nulls, cardinality, outliers)
  • Then write rules: Based on what the profile revealed + business requirements, write rules that check for the specific issues you found
  • Rules validate going forward: After you've profiled once and written rules, the rules check continuously
Q: Can OptSel and RptSel be in separate files/views?
▼
A: Yes. Typically:
  • [Schema].[RuleName_OptSel] — the full options view
  • [Schema].[RuleName_RptSel] — wraps OptSel to report only errors
Some projects put both in one view; others separate them. Either way, the logic is the same.

Session 2: SQL Best Practices for DQ Rules

Session 1 taught you the concepts (OptSel/RptSel, dimensions, lifecycle). This session teaches you the exact SQL dialect the Syniti Methodology Studio requires — the same standard applied to every rule, whether it was hand-written, locally derived, or AI-generated.

Why a Dialect, Not Just "SQL"

Standard SQL is flexible — there are dozens of valid ways to write the same query. DQ rules can't afford that flexibility, because:

  • Rules must be auditable by someone without deep SAP expertise
  • Rules must be comparable across hundreds of similarly-shaped rules
  • Rules must never leak data across source systems in a multi-system landscape
  • Rules generated by AI must reach the same structural quality as rules written by hand — the dialect is what makes that possible

What You'll Learn in This Session

  1. CTEs — when to use them, and the rules that make them safe
  2. zSourceSystemID Filtering — the single most important, most frequently missed rule
  3. Comment Standard — the mandatory header block and inline commenting rules
  4. Aliasing & Naming — zConcatenatedKey, rule-name limits, acronym preservation
  5. Complete Example — the Session 1 material rule, now fully compliant
  6. What a Good Rule Looks Like — a single checklist tying every rule together

Everything in this session is a rule you must follow, not a stylistic suggestion. A rule that's logically correct but violates the dialect (e.g., missing zSourceSystemID filtering) is still considered wrong.

Common Table Expressions (CTEs)

A CTE (the WITH ... AS (...) block at the top of a query) lets you name an intermediate result and reuse it later in the same query. In DQ rules, CTEs are the standard way to pre-aggregate or pre-filter a related table before joining it to the main table.

When to Use a CTE

  • Pre-aggregating a child table before joining it to the master (e.g., counting sales orders per material)
  • The rule needs to check a related table's status, and the join chain is easier to read as a separate step
  • A multi-table check is clearer broken into named steps rather than one deeply nested query

The CTE Rules (All Are Mandatory)

1
Every CTE must be used. If you define a CTE, it must be joined or selected from in the outer query. An unused CTE doesn't just add clutter — some engines will error on it, and it always signals unfinished logic.
2
Every CTE must output zSourceSystemID. Select it explicitly from the base table inside the CTE, even if nothing else in the CTE needs it — the outer query needs it to join safely.
3
Every CTE must filter on zSourceSystemID internally. Inside the CTE's own WHERE, reference the main table's system ID so the CTE never mixes data from two source systems before it's even joined.
4
Every join to a CTE must include a zSourceSystemID equality alongside the natural key columns — the same rule that applies to joining two base tables applies to joining a CTE.
5
The CTE is an implementation detail, not a shape change. The view's outer SELECT must still expose the five field sections in order (Technical → Basic → Org → Value → Activity). Using a CTE internally never changes what the view looks like from the outside.

Worked Example: Pre-aggregating a Child Table

Scenario: Flag materials that have zero sales orders — the rule needs a count from a child table (VBAP, sales order items) before it can decide.

-- ============================================================ -- DQ Rule: Material must have at least one sales order line -- Rule ID: MM-0042 -- View: Opportunity View (OptSel) -- Generated: 2026-08-18 -- Target: MS SQL Server -- ============================================================ WITH order_summary AS ( -- Count sales order lines per material, scoped to the same source system SELECT vbap.zSourceSystemID, vbap.MATNR, COUNT(*) AS order_line_count FROM vbap -- Sales order item table WHERE vbap.zSourceSystemID = 'Z01' -- CTE-level system filter (mandatory) GROUP BY vbap.zSourceSystemID, vbap.MATNR ) SELECT -- Syniti Technical Fields mara.zSourceSystemID, CONCAT(mara.zSourceSystemID, '_', mara.MATNR) AS zConcatenatedKey, CASE WHEN order_summary.MATNR IS NULL THEN 1 -- No sales order lines found = error ELSE 0 END AS zIsErrorFlag, -- Basic Fields mara.MATNR, mara.MAKTX, -- Activity Context mara.ERSDA FROM mara LEFT JOIN order_summary ON mara.zSourceSystemID = order_summary.zSourceSystemID -- CTE join carries zSourceSystemID AND mara.MATNR = order_summary.MATNR WHERE mara.zSourceSystemID = 'Z01' -- Main table system filter (mandatory) AND mara.LVORM = '' -- Exclude materials marked for deletion

Notice: the CTE (order_summary) is used in the outer join, filters on zSourceSystemID internally, and outputs zSourceSystemID so the outer join can match it safely. The outer query still shows Technical Fields first, then Basic, then Activity Context — the CTE never changed that shape.

zSourceSystemID Filtering — Mandatory Everywhere

This is the single most important, and most frequently missed, rule in the entire dialect. In a multi-system landscape, without this filter a rule can silently mix data from two different SAP systems and produce a meaningless result.

The Four Places It Must Appear

1. Main Table WHERE Clause

The primary table in the FROM clause must always carry a WHERE filter on zSourceSystemID:

FROM MARA LEFT OUTER JOIN ... WHERE MARA.zSourceSystemID = '<system>'

2. Every Join's ON Clause

When a join's ON clause equates the same field name across two tables (a cross-table parity/lookup check — not a foreign-key-to-description join), pair it with a zSourceSystemID equality:

ON t001.zSourceSystemID = t009.zSourceSystemID AND t001.PERIV = t009.PERIV

This applies to joins inside a CTE's own joins too — a CTE is never exempt from this rule.

3. Every CTE's Internal WHERE

Any CTE sourcing from a base table filters on zSourceSystemID in its own WHERE, referencing the main table's value:

WITH cte AS ( SELECT ... FROM table_a WHERE zSourceSystemID = <main_table>.zSourceSystemID )

4. Every Join to a CTE's Output

FROM main_table LEFT JOIN cte ON main_table.zSourceSystemID = cte.zSourceSystemID AND main_table.key_field = cte.key_field

Two Things You Must Never Write

✗
Never write a literal: 'Z01' AS [zSourceSystemID]. It is always a live column reference off the driving table — a literal defeats the purpose of the filter entirely.
✗
Never hardcode MANDT against a fixed client number anywhere in the SQL. Like zSourceSystemID, it is always a column reference, never a constant.

Why This Matters

Picture a rule that joins MARA (materials) to T006 (units of measure) without a zSourceSystemID pairing. If both systems load their own T006 rows into the same physical table, the join can match a material from System A against a unit-of-measure row that only exists in System B. The rule will produce a plausible-looking but wrong result — exactly the kind of silent failure this filter exists to prevent.

The Mandatory Comment Standard

Every generated rule — local, AI-derived, or bulk — must carry the same commenting discipline. The goal: a reader without SAP expertise can follow the business logic just from the comments.

1. The Header Block (Non-Negotiable)

Every SQL output begins with this exact format — never modified, abbreviated, or omitted:

-- ============================================================ -- DQ Rule: [Rule name received] -- Rule ID: [RuleID received] -- View: [Opportunity view or Report View] -- Generated: [Generation Date] -- Target: MS SQL Server -- ============================================================

Every bracketed placeholder is replaced with the real value — the rule's actual name, its ID, whether this is the OptSel ("Opportunity view") or RptSel ("Report View"), and the actual generation date.

2. Section Headers

Section headers use the simple dash format only:

-- Basic Fields -- Activity Context

Never a decorative bracket/equals wrapper like /* ===== Basic Fields ===== */. Keep section comments clean and minimal — they're signposts, not banners.

3. Every WHERE, JOIN, and CASE Needs a Comment

Each condition carries a /* ... */ or -- comment explaining its business meaning in plain language:

-- Identify active customers with no sales orders -- Join VBAK to determine order existence

That two-line example is the target style — the maximum, not a starting point to expand on. Comments explain only:

  1. The rule's purpose
  2. Important business logic
  3. Non-obvious joins

What Comments Must Never Do

✗
Narrate the SQL syntax line-by-line ("this selects the material number")
✗
Discuss performance tuning, indexing suggestions, or uniqueness confidence inline — that belongs in separate notes, never inside the SQL
✗
Mention AI, a model, or that the SQL (or any part of it) was generated or touched by one — every comment reads as ordinary engineering commentary, regardless of how the rule was produced

Why this matters: Comments are what make a rule auditable — one of the four properties of a good rule from Session 1's FAQ. A rule nobody can explain from its comments alone isn't finished, no matter how correct its logic is.

Aliasing & Naming Conventions

Consistent naming is what lets someone read a rule they've never seen before and immediately recognize its parts. These conventions apply across every rule in the Studio.

zConcatenatedKey — No Space, Underscore Delimiter

The alias is always written as one word: zConcatenatedKey. Two rules govern its construction:

✓
Always use _ (underscore) as the delimiter between concatenated parts. Never | (pipe) or any other delimiter — standardize to underscore across every zConcatenatedKey in the codebase.
✓
It must actually be unique at the query's grain. If a join fans the master record out to multiple child rows, the key must include enough of the child table's fields to stay unique per output row — not just the header table's key.
CONCAT(MARA.zSourceSystemID, '_', MARA.MATNR) AS zConcatenatedKey

Rule Name Length

Rule names are business-friendly sentences, not technical identifiers — but they still have hard limits:

  • Target: ≤ 85 characters
  • Absolute maximum: 100 characters

If a name doesn't fit, tighten the wording rather than abbreviating into something unclear — "Material must have valid base unit of measure" beats "Matl must have valid BUoM" even though the second is shorter.

Preserve SAP Acronyms

Never expand or lowercase standard SAP/business acronyms in rule names or comments. These stay exactly as written:

PIR · BOM · MRP · PO · SO · GL · AP · AR · UoM · CoA · FI

"Material must have valid base UoM" is correct. "Material must have valid base unit of measure" is also acceptable prose, but never write "uom" lowercase or spell out "Unit of Measure" inconsistently within the same rule set.

Field Section Order (Recap from Session 1)

Every generated rule's SELECT exposes fields in this exact order — this is a naming/structuring convention as much as a technical one:

  1. Syniti Technical Fields — always exactly zSourceSystemID, zConcatenatedKey, zIsErrorFlag, in that order, always first
  2. Basic Fields — identification/descriptive data answering "what is this record?" (material number, customer ID, name, description)
  3. Organizational Context — structural/hierarchical fields answering "where in the org does this belong?" (cost center, company code, plant, division) — never put these in Value Context
  4. Value Context — only money, amounts, prices, rates, currencies — "how much is this worth?" — never dates, never org fields
  5. Activity Context — only dates, times, temporal fields — "when did this happen?" — never monetary values, never org fields

What a Good Rule Looks Like

This is the single checklist that ties Session 1 (concepts) and Session 2 (dialect) together. Run any rule — yours or someone else's — through this list before considering it finished.

Business Correctness

✓
The SQL actually tests what the rule name says. A rule named "vendor must have a tax ID" whose CASE checks something else is wrong, no matter how clean the SQL is.
✓
The error condition lives in the CASE, not the WHERE. OptSel returns the whole universe; WHERE is only for scope (system filter, deletion-flag exclusions) — never for the condition that makes a record "bad".
✓
Deletion flags and status fields aren't confused. Deletion flags (LVORM, LOEKZ, LOEVM) exclude records in WHERE. Status fields (MMSTA, PSTAT, STATU) drive the flag in CASE. The same condition never appears in both places.

Structural Correctness

✓
zIsErrorFlag is INTEGER 1/0 — never 'Yes'/'No' or any text value.
✓
RptSel is a pure wrapper: SELECT * FROM OptSel WHERE zIsErrorFlag = 1 — nothing more, nothing less.
✓
All five field sections are present, in order: Syniti Technical Fields → Basic Fields → Organizational Context → Value Context → Activity Context.
✓
zSourceSystemID filtering is present everywhere required: main table WHERE, every join's ON clause, every CTE's internal WHERE, every join to a CTE's output.
✓
Every CTE is used — none are dangling — and each one outputs and filters on zSourceSystemID.
✓
zConcatenatedKey is unique at the query's grain and built with underscore delimiters.

Documentation Correctness

✓
The header block is present and complete — rule name, rule ID, view type, generation date, target platform.
✓
Every WHERE, JOIN, and CASE has a plain-language comment explaining the business reason — readable by someone without SAP expertise.
✓
The rule name is ≤ 85 characters (target), never over 100, and preserves standard SAP acronyms (PIR, BOM, MRP, PO, SO, GL, AP, AR, UoM, CoA, FI) exactly.
✓
The description follows Fetch / Check / Return — what data is fetched, what condition is checked, what the rule returns.

The Four Properties (From Session 1, Now Concrete)

Session 1's FAQ said good rules are business-defined, measurable, auditable, and actionable. This checklist is what those four words mean at the SQL level:

  • Business-defined → the SQL tests what the name says (Business Correctness)
  • Measurable → zIsErrorFlag is a clean 1/0 integer you can count (Structural Correctness)
  • Auditable → the header block and inline comments let anyone follow the logic (Documentation Correctness)
  • Actionable → RptSel isolates exactly the records someone needs to fix (Structural Correctness)

A rule that fails even one item above is not done yet — regardless of who or what wrote it. This checklist applies identically to hand-written, locally-derived, and AI-generated rules.
