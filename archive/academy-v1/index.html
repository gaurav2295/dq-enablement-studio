Create Account & Session Setup

Before you can derive rules, you need to create a Studio account and perform initial setup.

Account Creation

Step 1: Register

  • Visit the Syniti Methodology Studio login page
  • Click "Create New Account"
  • Provide your email, name, and organization
  • Set a secure password (minimum 12 characters, mix of upper/lower/numbers/symbols recommended)
  • Verify your email address via the confirmation link

Step 2: First Login & Initial Setup

  • You'll be prompted to set your timezone (used for audit timestamps)
  • Select your primary language (English, German, or Spanish)
  • Accept the methodology standards (Session 2's checklist)
  • You're now in the Dashboard — ready to configure your first session

What Happens During Account Setup

✓
You receive read-only documentation access — the methodology vault, rule templates, and best-practice SQL examples
✓
Your organization is created automatically — you can invite colleagues to the same org later via Settings
✓
Audit trails are initialized — every rule derivation, AI enhancement, and export is timestamped and logged to your organization's history

Key Account Settings to Know About

  • Timezone: Controls when scheduled bulk derivations run (e.g., "run nightly at 9pm your local time")
  • Language: Affects UI text, but rule SQL output is always English
  • Org Permissions: Which colleagues can see your rules; defaults to "Private" (only you)
  • Export Format: Choose SQL, T-SQL, or Snowflake dialect for your target database

Session Configuration: Systems & API Keys

A "Session" in the Studio is where you connect to your data sources, configure API keys, and define the systems you want to derive rules for. Think of it as a project that combines data + AI settings.

What is a Session?

A Session is the operational container for your rule-derivation work. Each Session has:

  • System Connections: Links to your SAP ECC, S/4HANA, or other data sources
  • API Keys: Credentials to call Claude (for AI enhancement) or other external services
  • Configuration: Settings for how rules are derived and exported
  • Derivation History: Every rule you create, derive, or enhance in this session

Creating a New Session

Step 1: From the Dashboard, click "New Session"

  • Give it a descriptive name (e.g., "SAP ECC Migration - Phase 1", "S/4HANA Master Data Prep")
  • Describe its purpose (optional, but helpful for future reference)
  • Select your target database platform: SQL Server, SAP HANA, Snowflake, or BigQuery

Step 2: Configure System Connections

  • Add each SAP system you want to derive rules for (System ID, System Client, Host, Port)
  • Provide database credentials (read-only access is sufficient — the Studio never writes to your systems)
  • Test the connection — the Studio will query a small set of tables to verify access

Step 3: Set Up API Keys (For AI Enhancement)

  • If you plan to use AI enhancement (optional), provide your Claude API key
  • Go to your Claude account settings and generate an API key if you don't have one
  • Paste it into the Session's API Keys configuration
  • The Studio never displays this key after you save it — only stores it encrypted

System ID Best Practices

✓
Use a consistent naming convention. If your systems are "Z01" (Production), "Z02" (Quality), "Z03" (Development), stick with that nomenclature in the Studio.
✓
Map to zSourceSystemID. The System ID you enter here becomes the value in every rule's zSourceSystemID filter (Session 2 requirement).
✓
One system per connection. Don't try to connect multiple systems with one credential — each gets its own entry so the Studio can derive rules scoped correctly.

After Configuration

Once systems and API keys are configured, the Session is ready for rule derivation. You can now:

  • Derive individual rules one at a time
  • Import a bulk list of rules to derive all at once
  • Use AI enhancement to improve or rewrite existing rules

Checkpoint: Your Session is now live with system connections and API keys in place. You're ready to derive your first rule.

Derive Your First Rule

With your Session configured, it's time to create and derive your first DQ rule. The Studio supports two derivation methods: Local Derivation (deterministic) and AI Enhancement (optional, with Claude).

Rule Derivation Overview

When you derive a rule, you tell the Studio:

  1. What table to check (e.g., MARA for materials)
  2. What the error condition is (what makes a record "bad")
  3. What the scope is (inclusions and exclusions)

The Studio then generates OptSel and RptSel SQL views that follow every standard from Session 2.

Step-by-Step: Your First Derivation

Step 1: Start a New Rule

From the Session dashboard, click "New Rule" → "Start Derivation".

Step 2: Define the Rule in Business Terms

You'll be asked:

  • Rule Name: Business-friendly (≤ 85 characters target). Example: "Material must have valid, non-deleted base unit of measure"
  • Rule Description: Use the Fetch / Check / Return template. Example: "Fetch all materials from MARA where LVORM is empty (not deleted). Check that MEINS (base UoM) exists and is valid in table T006. Return all materials, flagging as error (zIsErrorFlag=1) if MEINS is NULL or not found in T006."
  • Primary Table: Select MARA (materials)
  • System: Choose which system(s) this rule applies to

Step 3: Define Scope (Inclusions & Exclusions)

Inclusions: Who does this rule apply to? (optional)

  • Example: Only check materials where zSourceSystemID = 'Z01' (production system)
  • Example: Only check materials where MTART = 'FERT' (finished goods)

Exclusions: Who should be skipped? (highly recommended for deletion flags)

  • Example: Exclude materials where LVORM = 'X' (marked for deletion)

Step 4: Define the Error Condition

This is where you tell the Studio what "bad" means. You can:

  • Use the Rule Builder (UI): Click "Build Rule" and select conditions from dropdowns. The UI helps you avoid syntax errors.
  • Write SQL Directly: If you're comfortable with SQL, switch to "SQL Mode" and write the CASE condition directly.

Example using the Rule Builder:

Condition 1: MEINS [IS NULL]
OR Condition 2: MEINS [NOT IN] (SELECT MSEHI FROM T006 WHERE SPRAS='E')

Step 5: Select Fields to Include

Choose which fields appear in the rule output. The Studio will organize them into the five sections (Session 2):

  • Syniti Technical Fields: Always included (zSourceSystemID, zConcatenatedKey, zIsErrorFlag)
  • Basic Fields: MATNR, MAKTX (material ID and description)
  • Organizational Context: WERKS (plant), BWKEY (valuation area)
  • Value Context: VERPR (planned price)
  • Activity Context: ERSDA, AEDAT (created/modified dates)

Step 6: Preview & Generate

Click "Generate Rule". The Studio will:

  • Validate your input against Session 2 standards
  • Generate OptSel and RptSel SQL
  • Show you a preview of the generated SQL

Step 7: Review & Save

Check the generated SQL against Session 2's "What a Good Rule Looks Like" checklist. If it passes, click "Save Rule". The rule is now stored in your Session.

What the Studio Generated

Your rule now has:

  • OptSel View: All materials (in scope) with zIsErrorFlag = 1 or 0
  • RptSel View: Wrapper: SELECT * FROM OptSel WHERE zIsErrorFlag = 1 (errors only)
  • Comments: Header block, section headers, and inline business logic
  • Field Organization: Technical → Basic → Org → Value → Activity (Session 2)
  • zSourceSystemID Filtering: In main table WHERE and every join (Session 2)

Checkpoint: Your first rule is saved! You now have OptSel and RptSel SQL that follows every Session 2 standard. Next, you can run it, enhance it with AI, or move on to derive more rules.

Deterministic Derivation: How It Works

Every time you derive a rule using the Studio's local derivation engine (without AI), you get the exact same SQL output — same structure, same comments, same field organization. This is "deterministic derivation."

Why Deterministic Derivation Matters

✓
Consistency: Every rule derived in your organization follows the same pattern. Auditors and reviewers recognize the structure immediately.
✓
Reproducibility: If you derive the same rule again next month, you get identical SQL (unless you change the input). No surprises, no hidden logic.
✓
Version Control Friendly: Same SQL means git diffs are predictable — you see only the logic you changed, not formatting or random variable ordering.
✓
Regulatory Audit Ready: Deterministic output is easier to certify. You can show regulators: "Here's the rule, here's how it was generated, generate it again, you get the same output."

What the Deterministic Engine Does

When you fill in the Rule Builder form and click "Generate", the Studio's local derivation engine:

1. Validates Input

  • Rule name ≤ 85 characters (target) / ≤ 100 (absolute max)
  • Description follows Fetch / Check / Return template
  • Primary table exists and is accessible in the configured system
  • Inclusions and exclusions are syntactically valid
  • Error condition is written in SQL or properly translated from the UI builder

2. Builds the OptSel Query

  • Generates the FROM/JOIN structure: If you referenced related tables (e.g., T006 for valid UoMs), the engine builds the JOINs automatically with zSourceSystemID parity
  • Composes the CASE statement: Your error conditions become the CASE branches. 1 = error, 0 = clean.
  • Organizes the SELECT: Fields are ordered per Session 2: Technical → Basic → Org → Value → Activity
  • Applies WHERE filters: Inclusions go in WHERE; exclusions (especially deletion flags) go in WHERE to exclude out-of-scope rows

3. Adds Session 2 Compliance

  • Header block: DQ Rule name, Rule ID, view type, generation date, target platform
  • Comments: Section headers (Syniti Technical Fields, Basic Fields, etc.) and inline business-logic comments
  • zSourceSystemID: Main table WHERE and every join ON carries the system filter
  • zConcatenatedKey: Built as CONCAT(zSourceSystemID, '_', primary_key)

4. Generates RptSel as a Wrapper

SELECT * FROM [RuleName_OptSel] WHERE zIsErrorFlag = 1

5. Returns Preview & Stores Rule

The Studio shows you the generated SQL for review. If you approve, it saves both OptSel and RptSel to your Session, timestamped with metadata (who created it, when, what version of the derivation engine).

Determinism in Action: Example

You derive a rule three times, with identical inputs:

Input: Table=MARA, Error Condition=MEINS IS NULL, Exclusion=LVORM='X'
Run 1 (March 2026) → Output A (saved)
Run 2 (May 2026, same input) → Output A (identical)
Run 3 (July 2026, same input) → Output A (still identical)

The SQL is exactly the same all three times. Same field order, same comment structure, same zSourceSystemID placement. This is deterministic.

When Determinism Changes

If you change the input (e.g., add a new exclusion or include a different field), the engine re-derives with the new logic. The output changes, but it's still deterministic — the same new input always produces the same new output.

AI Enhancement: What Claude Does & What Instructions Are Sent

After you've derived a rule (deterministically), you can optionally send it to Claude for AI enhancement. Claude can improve the SQL, add complexity, or rewrite it entirely while maintaining Session 2 compliance.

What is AI Enhancement?

AI Enhancement is a separate pass that:

  • Takes your derived rule (OptSel + RptSel)
  • Sends it to Claude with a detailed specification
  • Asks Claude to improve, rewrite, or enhance the SQL
  • Returns Claude's suggestions for you to review and accept/reject

Important: AI Enhancement is optional. Your deterministically-derived rule is fully valid on its own. Use AI Enhancement only if you want Claude's expert suggestions.

When to Use AI Enhancement

  • Complex multi-table rules: Claude can simplify CTEs or suggest better join strategies
  • Performance tuning: Ask Claude to optimize for large datasets
  • Cross-system checks: Claude can help design rules that safely compare data across multiple systems
  • Compliance complexity: Rules that need to handle edge cases or regulatory requirements
  • Learning: Compare Claude's version to your derived version to see how it thinks about SQL

The AI Enhancement Instructions (What Claude Receives)

When you click "Enhance with AI" in the Studio, Claude receives a structured prompt that includes:

1. The Rule Specification

Claude gets:

  • Rule name and description
  • Primary table and scope (inclusions/exclusions)
  • Error condition in plain English
  • List of systems the rule applies to (e.g., "Z01=Production, Z02=Quality")
  • Target database platform (SQL Server, SAP HANA, etc.)

2. Session 2 Compliance Requirements

Claude is explicitly told:

  • Field section order: Technical → Basic → Org → Value → Activity (always)
  • zSourceSystemID filtering: Must appear in main table WHERE, every join ON, every CTE internal WHERE, and every CTE join
  • Header block format: Exact format with rule name, ID, view type, generation date
  • Comment standard: Section headers + inline business-language comments (no technical narration)
  • zIsErrorFlag: Must be INTEGER 1/0, never text
  • CTE rules: Every CTE used, filters/outputs zSourceSystemID, properly joined
  • zConcatenatedKey: Built with underscore delimiters, unique at the query grain

3. The Current Derived SQL

Claude gets your rule's current OptSel and RptSel to use as a baseline. Claude understands: "Here's what the deterministic engine produced — improve on this while maintaining all compliance requirements."

4. Domain Context

Claude receives relevant background:

  • SAP table schemas and relationships relevant to this rule
  • Standard SAP abbreviations (UoM, CoA, PIR, BOM, etc.)
  • Business context (e.g., "this is for an S/4HANA migration" or "this is for ongoing quality monitoring")

5. Enhancement Goals

Claude is told what improvement you're seeking:

  • "Improve readability" → Simplify CTEs, clarify logic
  • "Optimize for performance" → Add indexes hints (if applicable), simplify joins
  • "Handle edge cases" → Expand CASE logic to cover more scenarios
  • "Compare across systems" → Design multi-system fan-out (see "Sibling Rules")

Example: What Claude Receives

Rule Name: "Material must have valid, non-deleted base unit of measure"
Description: [Fetch/Check/Return template filled in]
Primary Table: MARA (materials)
Inclusions: zSourceSystemID='Z01'
Exclusions: LVORM='X' (marked for deletion)
Error Condition: MEINS is null OR MEINS not in valid UoM list (T006)
Target Platform: SQL Server
Current OptSel: [Your rule's SQL]
Goal: Improve readability and performance on large datasets
Compliance Requirements: [Session 2 standards, field sections, zSourceSystemID rules, comment standard, etc.]

What Claude Returns

Claude analyzes your rule and returns:

  • Improved OptSel SQL: Enhanced version following all compliance requirements
  • Improved RptSel: Updated wrapper (usually just a SELECT * from the new OptSel)
  • Explanation: Why Claude made each change, what improves, performance gains (if any)
  • Alternative Approaches: Claude often offers multiple strategies with trade-offs

How to Interpret Claude's Suggestions

When Claude returns an enhancement:

  1. Read the Explanation: Understand why Claude made changes
  2. Check Session 2 Compliance: Run Claude's SQL against the "What a Good Rule Looks Like" checklist
  3. Review Field Order: Are Technical → Basic → Org → Value → Activity respected?
  4. Verify zSourceSystemID: Appears in all four mandatory places?
  5. Test the SQL: If possible, run it on your test system and compare row counts with your original
  6. Accept or Modify: You can accept Claude's version, modify it, or keep your original

Sibling Rules & Multi-System Fan-out

In multi-system landscapes, the same business rule often applies to multiple SAP systems (Production, Quality, Development) or across different ERP tenants. "Sibling rules" are versions of the same rule scoped to different systems. This section explains how they work and how AI enhancement handles them.

What Are Sibling Rules?

When you derive a rule that applies to multiple systems (e.g., Z01, Z02, Z03), the Studio creates a primary rule + sibling variants, each with its own zSourceSystemID filter.

Example: You derive a rule for materials across three systems:

  • Primary: "Material must have valid UoM" (Z01 = Production)
  • Sibling 1: "Material must have valid UoM" (Z02 = Quality)
  • Sibling 2: "Material must have valid UoM" (Z03 = Development)

Each sibling runs independently, scoped to its own system. The logic is identical; only the zSourceSystemID filter changes.

Why Siblings Matter

✓
System Isolation: A rule for Z01 never accidentally includes rows from Z02. Each system's data stays separate.
✓
Bulk Derivation: Derive one rule definition once; the Studio automatically generates siblings for all configured systems.
✓
Consistency: All siblings have identical logic — only zSourceSystemID changes. Easy to audit and compare.
✓
Maintenance: Update the parent rule once; all siblings inherit the change automatically.

How AI Enhancement Works with Siblings

When you ask Claude to enhance a rule with siblings, the Studio:

Step 1: Send the Primary Rule to Claude

Claude receives the parent rule definition and returns enhanced SQL.

Step 2: Mechanically Derive Siblings

The Studio takes Claude's enhanced SQL and mechanically creates siblings by:

  • Replacing the primary system's zSourceSystemID value with each sibling's system ID
  • Updating view names to reflect the sibling (e.g., rule_name_Z01_OptSel, rule_name_Z02_OptSel)
  • Keeping all other logic identical

Step 3: Validate Sibling Compliance

Each sibling is validated against Session 2 standards automatically. If any sibling fails, the entire enhancement is rejected for safety.

Example: Fan-out in Action

Scenario: Your Session has three systems configured (Z01, Z02, Z03). You derive a material UoM rule as multi-system.

Input:
Rule Name: "Material must have valid UoM"
Systems: Z01 (Production), Z02 (Quality), Z03 (Development)
Error Condition: MEINS IS NULL OR MEINS NOT IN T006

Output:
Primary Rule (Z01):
- mm_material_valid_uom_z01_OptSel
- WHERE MARA.zSourceSystemID = 'Z01' AND ...

Sibling Rule (Z02):
- mm_material_valid_uom_z02_OptSel
- WHERE MARA.zSourceSystemID = 'Z02' AND ...

Sibling Rule (Z03):
- mm_material_valid_uom_z03_OptSel
- WHERE MARA.zSourceSystemID = 'Z03' AND ...

AI Enhancement & Sibling Substitution

When Claude enhances a sibling rule:

  1. Claude receives one logical rule definition (not the SQL yet, just the spec)
  2. Claude returns optimized SQL for that one rule
  3. The Studio automatically creates siblings by mechanical substitution of view names and zSourceSystemID values
  4. No AI is re-run per sibling — it's efficient and consistent

This avoids the problem of Claude making slightly different optimization choices for each system, which would make siblings hard to compare and audit.

Bulk Rule Execution

Once you've derived rules (with or without AI enhancement), you can run them all at once against your data. Bulk execution lets you execute hundreds of rules simultaneously and export the results.

What is Bulk Execution?

Bulk Execution is the operation that:

  • Takes all rules in your Session (or a selected subset)
  • Runs each rule's OptSel and RptSel SQL against your configured systems
  • Collects results: error counts, clean counts, sample failing rows
  • Optionally generates a report or exports the rules to your database

When to Use Bulk Execution

  • First-time data profiling: Run 50+ rules against a new dataset to get a baseline of data quality
  • Pre-migration: Execute all rules before an SAP migration cutover to identify issues early
  • Ongoing monitoring: Schedule bulk runs weekly or monthly to track quality trends
  • Deployment: Export all rules to your production database at once

Running a Bulk Execution

Step 1: Select Rules

  • From the Session dashboard, click "Bulk Execute"
  • Choose which rules to include: "All rules", "Only derived rules", "Only AI-enhanced rules", or "Select specific rules"

Step 2: Configure Execution

  • Target System: Which system to run against (Z01, Z02, Z03, etc.)
  • Database Connection: Confirm the database credentials
  • Timeout: How long to wait for all rules to complete (default: 30 minutes)
  • Collect Sample Data: Should the execution also pull a sample of failing rows? (helpful for understanding errors, but takes more time)

Step 3: Execute

  • Click "Start Bulk Execution"
  • The Studio runs all selected rules in parallel (with smart queuing to avoid overload)
  • Progress updates appear in real-time on the dashboard

Step 4: Review Results

Once complete, you see a summary:

  • Total Rules Run: X rules executed successfully
  • By Status: Y rules found errors, Z rules found zero errors
  • Error Rate: Aggregate: "Total records checked: 1M, Errors found: 15K (1.5%)"
  • Per-Rule Breakdown: Sortable table showing each rule's name, error count, clean count
  • Sample Failing Rows: If enabled, first few rows from each rule's RptSel (errors only)

Bulk Execution Output

After execution, you can:

1. Export the Rules to Your Database

  • Click "Export to Database"
  • Choose the target schema and naming convention
  • The Studio generates CREATE VIEW statements for all OptSel and RptSel views
  • You can execute the SQL immediately or download it for your DBAs

2. Generate a Data Quality Report

  • Click "Generate Report"
  • The Studio creates a PDF or Excel report showing error trends, top failing rules, system-by-system breakdown
  • Useful for stakeholder communication

3. Download Results as CSV

  • Each rule's results (error count, clean count, sample data) can be downloaded as CSV for further analysis

Bulk Execution Best Practices

✓
Start with a small set: Run 5–10 rules first to check that your systems are configured correctly, then scale to hundreds.
✓
Run during off-hours: Bulk execution can consume database resources. Schedule for nights or weekends when your systems are quiet.
✓
Monitor for performance issues: If a rule runs slowly, review its CASE logic and JOINs. Use AI enhancement to optimize.
✓
Keep sample data collection reasonable: Collecting samples from 100+ rules can slow execution. Sample only if you need it.

How to Interpret Claude's Output

When Claude returns an AI-enhanced rule, you get more than just SQL. Understanding Claude's feedback helps you make informed decisions about whether to accept, modify, or reject the enhancement.

What Claude Returns

Claude's response includes:

1. The Enhanced SQL (OptSel)

Claude provides the complete, production-ready OptSel query with:

  • Header block (completed with your rule name, ID, etc.)
  • CTEs (if used) with zSourceSystemID filtering
  • SELECT with all five field sections in order
  • CASE statement with error conditions
  • WHERE clause with scope (zSourceSystemID, deletions, inclusions/exclusions)
  • Comments throughout

2. The Enhanced RptSel (Wrapper)

Claude typically leaves RptSel as-is (it's just a wrapper), but may suggest optimizations.

3. Explanation: What Changed

Claude explains:

  • What was wrong or inefficient in your original rule
  • What Claude changed and why
  • Expected improvements (performance, clarity, compliance)

Example explanation from Claude:

"Your original rule joined MARA directly to T006 without aggregation, which could fan out the result if T006 has duplicate UoM entries per system. I've added a CTE that pre-aggregates T006 (SELECT DISTINCT zSourceSystemID, MSEHI FROM t006) to ensure a one-to-one join. This prevents duplicate error flags and improves performance on large datasets. The CTE maintains zSourceSystemID filtering as required."

4. Alternative Approaches (Optional)

Claude may offer alternatives with different trade-offs:

  • Option A (Recommended): [Enhanced SQL] — Balances performance and readability
  • Option B: [Alternative SQL] — Simpler but may be slower on large datasets
  • Option C: [Alternative SQL] — Highly optimized but more complex CTEs

How to Evaluate Claude's Suggestions

Step 1: Check Session 2 Compliance

✓
Does the SQL have the header block with rule name, ID, view type, date, and target platform?
✓
Are the five field sections in order? (Technical → Basic → Org → Value → Activity)
✓
Does every WHERE, JOIN, and CASE have a business-language comment?
✓
Is zSourceSystemID filtered in the main table WHERE and every join ON clause?
✓
If there are CTEs, does each filter on zSourceSystemID internally and output it?
✓
Is zIsErrorFlag an INTEGER (1/0), never text?

Step 2: Verify Business Logic

  • Does the CASE statement match your original error condition? Or did Claude improve it?
  • Are all your exclusions (deletion flags, etc.) still in the WHERE?
  • Did Claude add complexity that makes sense, or overcomplicate the rule?

Step 3: Test on Sample Data (If Possible)

  • Run Claude's SQL against your test system
  • Compare row counts: Does Claude's OptSel return the same or similar number of rows as your original?
  • Check a few error records: Do they make business sense?

Common Issues and How to Interpret Them

Issue: Claude's SQL is Much Longer Than Your Original

Interpretation: Claude probably added CTEs or more complex CASE logic. This isn't bad — it often means Claude found edge cases or optimized for performance. Review Claude's explanation. If satisfied, accept. If unsure, ask Claude for Option B (simpler approach).

Issue: Claude Warns That Your Original Violated a Session 2 Standard

Interpretation: Claude found a compliance issue (missing zSourceSystemID filter, wrong field order, etc.). This is valuable feedback — accept Claude's corrected version.

Issue: Claude Suggests Adding a CTE, But You're Not Sure It's Needed

Interpretation: Claude likely added it to prevent fan-out (one-to-many join problem) or improve performance. Read Claude's explanation. CTEs aren't free (slight overhead), so they should add value. If Claude's explanation is convincing, accept. Otherwise, choose Option B (simpler).

Issue: Claude's Output is Completely Different From Your Original

Interpretation: Claude re-thought the entire rule. This happens when Claude finds a fundamentally better approach. Read the explanation carefully. If it still tests the same error condition (same business logic), and passes Session 2 checks, it's probably good. If it changes the logic, ask Claude why — you might need to clarify the original requirement.

Accepting vs. Rejecting an Enhancement

Accept Claude's Enhancement If:

  • It passes Session 2 compliance fully
  • It tests the same (or improved) business logic
  • Claude's explanation is clear and makes sense
  • You've tested it and the results are reasonable

Reject or Modify If:

  • It violates Session 2 standards (missing zSourceSystemID, wrong field order, etc.)
  • It changes the business logic in ways you didn't ask for
  • You test it and error counts are wildly different from your original
  • You're uncomfortable with a choice Claude made (too complex, not complex enough, etc.)

Apply Corrected SQL

After Claude returns an enhancement, or if you manually fix a rule's SQL, you use "Apply Corrected SQL" to save the updated version to your Session and, optionally, to all sibling rules at once.

The "Apply Corrected SQL" Workflow

Scenario 1: Accepting Claude's Enhancement

Claude returns an enhanced rule. You review it, pass all compliance checks, and decide to use it.

  1. In the Studio, click "Accept Enhancement" on Claude's response
  2. The Studio shows you a diff: original SQL vs. Claude's SQL (highlighting what changed)
  3. You confirm by clicking "Apply Corrected SQL"
  4. The rule is updated with Claude's version and marked with an audit trail: "Enhanced by Claude on [date]"

Scenario 2: Applying Corrections to Siblings

Claude enhanced your primary rule, and you want all siblings (Z01, Z02, Z03) to get the same enhancement.

  1. After accepting Claude's enhancement for the primary rule, the Studio prompts: "Apply to sibling rules?"
  2. Check "Apply to all siblings"
  3. Click "Apply Corrected SQL to All"
  4. The Studio mechanically applies Claude's SQL to all siblings, updating only zSourceSystemID and view names (no AI re-run needed)
  5. All siblings now have the same enhancement, each scoped to its own system

Scenario 3: Manual Corrections

You (or a colleague) manually edit a rule's SQL to fix a bug or improve it.

  1. In the Studio's SQL editor, make your changes
  2. Click "Validate" to check the SQL syntax and Session 2 compliance
  3. If validation passes, click "Apply Corrected SQL"
  4. You can choose to apply to siblings as well (same mechanical substitution)

What "Apply Corrected SQL" Does

  • Updates the Rule: The new SQL replaces the old version in your Session
  • Records Audit Trail: Timestamps the change, notes who made it and why (e.g., "Applied Claude enhancement v1")
  • Updates Siblings (Optional): If you choose, mechanically updates all sibling rules with the same logic, preserving their zSourceSystemID values
  • Invalidates Old Results: If you've already run bulk executions with the old SQL, those results are marked as "obsolete" so you don't accidentally report old error counts

Applying to Siblings: The Mechanics

When you "Apply Corrected SQL" to all siblings:

Original (Sibling Z02): WHERE MARA.zSourceSystemID = 'Z02' AND ... ↓ Apply Correction with Sibling Substitution ↓ New (Sibling Z02): WHERE MARA.zSourceSystemID = 'Z02' AND ... (same structure, only zSourceSystemID value preserved)

The Studio:

  • Takes Claude's SQL (or your manual correction)
  • For each sibling, replaces the primary system's zSourceSystemID with the sibling's system ID
  • Updates view names to match the sibling (e.g., rule_name_Z02_OptSel)
  • Keeps all logic identical
  • Validates each sibling against Session 2 compliance
  • If any sibling fails validation, the entire operation is rejected (fail-safe)

Best Practices for Applying Corrections

✓
Always validate before applying: Check Session 2 compliance (or let the Studio do it automatically). Don't apply broken SQL to siblings.
✓
Review the diff: Before applying to siblings, see exactly what's changing. The Studio shows original vs. new side-by-side.
✓
Re-run bulk execution after major changes: If you make significant corrections, re-run the rule against your data to confirm results are still reasonable.
✓
Keep an audit trail: Use the Studio's notes field to document why you made each correction (e.g., "Fixed fan-out issue per Claude suggestion", "Simplified CTE per performance profiling").
